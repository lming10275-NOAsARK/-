# 성마전설 3×3 EYES (Mega-CD) 한글화 — 분석 현황

최종 갱신: 2026-10-04 / 체크포인트 1

## 1. 자료 구조

업로드 ZIP 3개를 풀면 다음 구조입니다.

```
ext/boot/system_area.bin      32KB   메가CD 부트 영역
ext/files/                    683개  CD 내부 파일 (고정 크기 슬롯)
ext/chunks/                   4개 대형 DAT (조각 분할, 이어붙이기 필요)
```

### 파일 그룹 (고정 크기 = CD 섹터 슬롯 설계)

| 접두 | 개수 | 크기 | 섹터수 | 추정 용도 |
|---|---|---|---|---|
| `EV000xx.DAT` | 310 | 131,072 | 64 | **이벤트(대사/연출) — 최우선 분석 대상** |
| `00MAPxx.DAT` | 140 | 327,680 | 160 | 맵 그래픽 + 타일맵 |
| `SPLAYxx.DAT` | 92 | 368,640 | 180 | 전투/연출 스프라이트 |
| `SMONxx.DAT` | 65 | 57,344 | 28 | 몬스터 |
| `PLAYxx.DAT` | 37 | 49,152 | 24 | 플레이어 캐릭터 |
| `BNK0xx.DAT` | 18 | 131,072 | 64 | 뱅크(사운드/공용 리소스) |
| `_000PRG.DAT` | 1 | 327,680 | 160 | **메인 프로그램 (68000 코드)** |
| `_010MAP / _011EVT / _012PLY / _013SPLY / _014SMON / _015BNK` | 6 | - | - | 각 그룹의 인덱스/테이블 추정 |

파일 크기가 그룹별로 모두 동일 → 게임이 `LBA = 기준 + 인덱스 × 고정섹터수`로
직접 시크하는 **고정 슬롯 설계**입니다. 이는 한글화에 매우 유리합니다.
**번역 결과가 슬롯 크기만 넘지 않으면 파일 재배치 없이 교체 가능합니다.**

## 2. 인코딩 조사 결과 (중요)

### 2-1. Shift-JIS 아님 — 확정
전체 683개 파일을 Shift-JIS 2바이트 유효성 + 히라가나 밀도로 스캔했습니다.

- 상위 점수 파일(`SPLAY*`, `_000PRG`)을 모두 디코딩해 육안 검증한 결과
  **전부 그래픽 오탐**이었습니다.
- 예: `_000PRG.DAT` 0x25B5C → `ぢべひびぶびぶびぶびぶび…` 는
  0x82D1/0x82D4 가 반복되는 **픽셀 패턴**이지 문장이 아닙니다.
- 한자 대비 히라가나 비율이 실제 일본어 문장과 전혀 맞지 않습니다
  (SPLAY계열: 한자 14,000 vs 히라가나 300 → 난수).

→ **원본 제작자 메모의 경고가 정확했습니다. Shift-JIS 검색은 전부 폐기합니다.**

### 2-2. 커스텀 인코딩(폰트 인덱스) 사용으로 결론
일본어 평문이 어디에도 없으므로, 게임은 자체 글꼴 인덱스로 문자를 저장합니다.
따라서 **글꼴 비트맵 확보 → 인덱스↔문자 대응표 작성**이 선행되어야 합니다.

### 2-3. 1bpp / 2색 4bpp 글꼴 직접 탐색 — 실패
- 1bpp (16×16, 12×12) 글리프 패턴 스캔: 해당 없음
- 2색 4bpp 영역 스캔: `00MAP*` 15곳 적중 → 렌더링 결과 **글꼴 아님**(선형 비트맵)

→ 글꼴은 **압축되어 저장**되어 있습니다.

## 3. 핵심 발견 — 공용 압축 블록

EV 파일 310개를 2KB 블록 해시로 대조한 결과,
**EV 파일 약 190개가 동일한 16KB 블록을 공유**합니다.

- 위치: 각 EV 파일의 `0x13000 ~ 0x17000` (일부 파일은 `0x1B000`에 중복 배치)
- 샘플 저장: `samples/shared_blob_EV_0x13000.bin`

여러 이벤트가 공유하는 리소스 = **글꼴 또는 공용 메시지창 리소스**일 가능성이 매우 높습니다.

### 3-1. 내부 구조
0xFF 패딩으로 구분된 **압축 청크 5개**:

| 청크 | 오프셋 | 길이 |
|---|---|---|
| 0 | 0x0000 | 2142 |
| 1 | 0x0D00 | 2446 |
| 2 | 0x1A00 | 1686 |
| 3 | 0x2700 | 1686 |
| 4 | 0x3400 | 1686 |

### 3-2. 청크 헤더 (21바이트, 빅엔디안 워드)
```
00 06 | 08 3e | 07 02 | 00 12 | 07 02 | 00 0a | 07 a0 | 00 0a | 00 00 | ed 15 | 00
00 06 | 09 6e | 08 32 | 00 12 | 08 32 | 00 0a | 08 d0 | 00 0a | 00 00 | ed 15 | 00
00 06 | 06 76 | 05 42 | 00 12 | 05 42 | 00 0a | 05 dc | 00 0a | 00 00 | ed 15 | 00
```
- `0x0006`, `0x0012`, `0x000A`, `0xED15` 는 전 청크 공통 상수
- 가변 워드끼리 일정한 차이를 유지 (예: W1-W2 = 0x13C, W6-W2 = 0x9E)
  → VRAM 주소/전송 크기 파라미터로 추정
- **압축 데이터 본체는 헤더 직후 0x14 또는 0x15부터 시작**

### 3-3. 압축 포맷 (분석 진행중)
표준 메가드라이브 압축 시험 결과:
- **Kosinski: 불일치** (디코딩 실패)
- **Comper: 불일치** (106바이트 소비로 8KB 생성 — 퇴화, 오탐)

바이트 통계로 본 실제 포맷 추정 — **니블 단위 LZ/RLE, 0xF 이스케이프**:
- `0xF0~0xFF` 바이트가 전체의 **23.1%** → 명백한 제어 코드 영역
- 최빈값 `0xFC`(157회), `0xF1`(57), `0xF8`(54), `0xFE`(27)
- `0xF8` 뒤에는 항상 작은 수(0x09~0x2A) → **길이 인자를 받는 명령**
- 니블 스트림으로 읽으면 `F + 명령니블` 구조가 깔끔하게 맞아떨어짐
  (`FF` = 리터럴 니블 F, `F8 nn` = 긴 런, `FC` = 최빈 명령)
- 4bpp 그래픽을 니블 단위로 압축하는 설계와 정확히 부합

## 8. 확정된 텍스트 구조

```
EV*.DAT (각 131,072바이트 고정 슬롯)
├ 0x00000  그래픽 / 리소스
├ 0x0C800  이벤트 opcode 블록   (연출·이동·플래그·대사호출)
├ 0x13000  Kosinski 압축 그래픽 (EV 190개가 공유)
└ 0x14800  ★ 대사 텍스트 블록
   ├ +0x0000  워드 0x0008 = 포인터 테이블 시작 위치
   ├ +0x0008  16비트 포인터 배열 (엔트리별 시작 오프셋)
   └ +첫포인터~  텍스트 opcode + 실제 문자열 데이터
```

- 문자 인코딩: **자체 1바이트 코드** (0x01=あ, 0x02=い …), 한자는 **0xF0~0xF6 선행 2바이트**
- 폰트: `_000PRG.DAT` **0x29000** 에 16×16 1bpp 한자 약 1500자,
  **0x29C00** 에 8×16 반각(숫자·괄호·쉼표 등 극소수)
- 폰트 배열은 SJIS/JIS 순서가 아님 → 반드시 `3x3eyes.tbl` 로만 해석
- 주요 제어코드: `<br />` 줄바꿈, `<0xdb>` 페이지 넘김, `<arrow>`, `<speak>`,
  `<portrait_NN>` 초상화, `<wait_NN>` 대기, `<return_p>`

### 그래픽 오탐 차단 방법
문자 테이블이 거의 모든 바이트값을 문자로 매핑하므로, 그래픽 바이트도 '문자'로 풀립니다.
이를 막기 위해 런 단위로 다음 조건을 모두 요구합니다 (`is_dialogue()`):
1. 일본어 글자 6자 이상
2. 히라가나 3자 이상
3. 한자가 있거나 `。、？！` 문장부호 포함

### 추출 예시
```
EV00007.DAT 0x148ED
```

# 체크포인트 3 — 한글화 파이프라인 완성

## 13. 폰트 구조 확정

`_000PRG.DAT` **0x29000** 부터 **16×16 1bpp, 글리프당 32바이트**로 나열되어 있고,
**글리프 인덱스가 곧 문자코드**입니다. 렌더링으로 직접 확인했습니다
(0번=공백, 1번=あ … 가나 → 기호 → 숫자 → 전각영문 → 한자 1,508자 순).

코드 ↔ 글리프 대응 규칙 (실측으로 도출):

| 코드 | 글리프 인덱스 | 원래 내용 | 칸수 |
|---|---|---|---|
| 1바이트 `cc` (0x01~0xDA) | `cc` | 가나·기호 | 217 |
| 2바이트 `F0 xx` | `224 + xx` | 전각 영문 | 30 |
| 2바이트 `Fp xx` (p=1~6) | `p*256 + xx` | **한자** | 1,508 |

→ 한자 자리를 전부 비우면 **한글 음절 1,725칸** 확보. 한국어 게임 텍스트에 충분합니다.

## 14. 한글 배정 전략 — 용량까지 절약

단순히 한자 자리(2바이트)만 쓰면 번역문이 전부 2바이트가 되어 바이트 한도를 넘깁니다.
그래서 **빈도순으로 1바이트 자리부터 채웁니다.**

- 자주 쓰는 음절 217자 → **1바이트**
- 나머지 → 2바이트

1차 번역 배치(31건) 기준 사용 문자가 130종이라 **전부 1바이트로 배정**되었고,
일본어 원문(한자 2바이트 혼용)보다 오히려 바이트가 덜 듭니다.

한글 글리프는 설치된 TTF에서 16×16으로 래스터라이즈합니다
(기본 `NanumGothicCoding.ttf`, 임계값 110). `뷁`·`핥`·`빲` 같은 복잡한 음절도

# 체크포인트 6 — 조각 단위 번역 + 자동 축약

## 23. 그래픽 오탐 분리 (`tools/junk.py`)

문자 테이블이 거의 모든 바이트값을 문자로 매핑하기 때문에 그래픽 데이터도
일본어처럼 풀립니다. 실제 대사의 성질로 걸러냅니다.

판정 기준 (하나라도 걸리면 가짜):
1. 한 글자가 과도하게 반복 (6자 이상에서 45%, 12자 이상에서 30%)
2. 조사·문장부호(`のにをはがでとも、。？！『』「」♥`)가 하나도 없음
3. 한자 대비 히라가나 비율이 0.25 미만 (난수 바이트의 특징)

결과: **가짜 458건 분리, 실제 번역 대상 3,009건**.
분리된 항목은 `translation/script_junk.tsv` 에 보존됩니다(판정 재검토용).

## 24. 조각 단위 번역 — 비용 대비 효과가 가장 큼

대사는 제어코드(`<br />`, `<0xdb>`, `<return_p>`)로 끊긴 **문장 조각**의 조합이고,
같은 조각이 수십 곳에 재등장합니다. 그래서 통째로 번역하는 것보다
**조각을 번역해 메모리에 넣고 자동 조립**하는 쪽이 훨씬 효율적입니다.

```bash
python3 tools/tm.py translation/script_ko.tsv report 100   # 막고 있는 조각을 빈도순으로
#  → translation/glossary.tsv 에 '일본어조각<탭>한국어' 로 추가
python3 tools/tm.py translation/script_ko.tsv               # 자동 완성
```

용어집 200여 개를 넣자 **275건이 자동 완성**되었습니다. 등장인물 이름
(야쿠모·파이·링링·홍냥·룽·미호시·가우 등)을 먼저 넣는 것이 특히 효과적입니다.

### 그래픽 조각 통과 처리
대사 뒤에 그래픽 바이트가 붙어 한 항목 안에 가짜 조각이 섞인 경우가 많습니다.
이런 조각은 번역하지 않고 **원본 바이트 그대로 통과**시킵니다. 이 처리 하나로
자동 완성이 1건 → 218건으로 늘었습니다.

## 25. 일본어 잔존 문자는 원본 코드 보존

## 30. 0x00 패딩이 안전한지 검증 — 안전함 (버그 아님)

번역문이 원문보다 짧을 때 남는 자리를 `0x00` 으로 채우고 있었는데,
`0x00` 은 문자 테이블에 **정의되어 있지 않은 바이트**라 위험할 수 있었습니다.

문자열 3,467개의 앞뒤 바이트를 전수 조사했습니다.

| 위치 | 최빈 바이트 | 건수 |
|---|---|---|
| 문자열 **직전** | `0x00` | 3,153 / 3,467 |
| 문자열 **직후** | `0x00` | 2,812 / 3,467 |

→ **`0x00` 은 이 게임의 문자열 종결자**입니다. 따라서 0x00 패딩은 올바른 동작이며,
첫 0x00 에서 출력이 끝나고 뒤쪽은 무시됩니다. 코드에 근거를 주석으로 남겼습니다.

## 31. 진짜 위험 — 엔트리 진입점(opcode 영역) 덮어쓰기

텍스트 블록의 각 엔트리는 **텍스트 opcode로 시작**하고(`0x24` 출력, `0x06`/`0x12`/`0x13`
플래그 분기 등), opcode는 2바이트 오프셋으로 실제 대사 데이터를 가리킵니다.

런 추출기가 **opcode 바이트를 문자로 흡수**한 경우, 거기에 번역문을 쓰면
대사 분기가 통째로 깨집니다.

실측: 포인터 테이블 진입점에서 시작하는 런은 **3,467개 중 34개**로 적었습니다.

### 대응 — `build_patch.py` 안전장치
원본 EV 파일에서 포인터 테이블을 다시 읽어 **엔트리 진입점 3,780곳**을 집합으로 만들고,
삽입 지점이 그 집합에 들어가면 **쓰지 않고 건너뛰며 보고**합니다.

실제로 이번 빌드에서 **3곳이 차단**되었습니다. 없었다면 스크립트가 손상됐을 지점입니다.
